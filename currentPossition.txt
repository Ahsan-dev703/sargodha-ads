Sargodha Ads – Current Project Position and Architecture

1. Project Overview
This project is a full-stack marketplace web app called “Sargodha Ads”. The idea is to allow users in Sargodha to register, log in, verify their email, post ads, manage their listings, and browse products or services in a local marketplace.

The application is split into two major parts:
- Frontend: React + Vite app
- Backend: Node.js + Express API
- Database: MongoDB (likely via Mongoose)
- Authentication: JWT-based auth with HttpOnly refresh cookie and memory-based access token
- Email: verification, password reset, and account notifications

This is a real-world application structure with authentication, protected routes, email flows, and a dashboard-style UI. It is not just a static demo; it is structured to become a full marketplace platform.

3. What the current project is doing

Frontend responsibilities
The frontend is built in React and uses route-based navigation to separate public and private pages.

Public pages currently include:
- Home
- Login
- Register
- Forgot password
- Reset password
- Verify email
- Verify email pending

Protected pages include:
- Dashboard
- MyAds

This means the app already has the concept of user-authenticated access and page protection.

Backend responsibilities
The backend exposes REST APIs for:
- User registration
- Email verification
- Resend verification email
- Login
- Forgot password
- Reset password
- Refresh access token
- Logout
- Fetch current authenticated user

The backend also handles:
- password validation
- email validation
- JWT generation
- refresh-token rotation
- secure cookie management
- centralized error handling

4. Authentication architecture
This project is using a modern and safer auth pattern:
- refresh token stored in an HttpOnly cookie on backend
- access token kept in memory on frontend
- no access token in localStorage/sessionStorage

This is good from a security perspective because browser storage is vulnerable to XSS attacks, while HttpOnly cookies are much harder to read from JavaScript.

Current flow:
1. User signs up.
2. Backend creates user and sends verification email.
3. User verifies email.
4. User logs in.
5. Backend creates access token + refresh token.
6. Backend sends access token in response data and stores refresh token in HttpOnly cookie.
7. Frontend stores access token in memory only.
8. On refresh, the app should restore the session by hitting refresh-token endpoint.

This is exactly the correct direction for a secure app.

5. Important technical facts

Backend auth files
- backend/src/utils/jwt.js
  - Generates access token and refresh token
  - Verifies access token and refresh token

- backend/src/middleware/auth.middleware.js
  - Protects routes by checking Authorization header and JWT

- backend/src/controllers/auth.controller.js
  - Handles register/login/logout/refresh flows

- backend/src/services/refreshToken.service.js
  - Saves and rotates refresh tokens in database

Frontend auth files
- frontend/src/context/features/AuthContext.jsx
  - Holds auth state for user, loading, and isAuthenticated
  - Initializes session on app startup

- frontend/src/hooks/useAuth.js
  - Reads auth context

- frontend/src/services/api.js
  - Central API helper for making requests and refreshing expired tokens

- frontend/src/services/token.js
  - Keeps access token in memory only

This structure is solid and is the correct base for a production-like auth system.

8. Best next build order
The recommended sequence is very important.

Phase 1: Stabilize the core app
- fix any remaining auth edge cases
- verify protected routes work after refresh
- ensure refresh token rotation is consistent
- test login/logout and email verification thoroughly
- fix API error handling edge cases

Phase 2: Build the ad domain
- create Ad model in backend
- create CRUD APIs
- connect frontend forms to API
- allow user to create and view their ads

Phase 3: Listing pages and homepage
- build home page ad feed
- build detail page for each ad
- add filters, categories, and search

Phase 4: Seller dashboard and profile
- show user’s ads and analytics
- edit profile
- manage seller information

Phase 5: media and polish
- add ad photos
- make UI more modern and responsive
- add loading spinners, empty states, and alerts

Phase 6: deploy and production hardening
- environment security review
- production build checks
- database indexing
- API rate limiting
- CORS and cookie hardening

13. Important note about security
The project is already moving in the right direction by avoiding localStorage for tokens. That is good practice. For production, we should keep this rule throughout the app:
- never store JWT access tokens in localStorage or sessionStorage
- keep refresh tokens in HttpOnly cookies only
- use short-lived access tokens in memory
- secure cookies with httpOnly, secure, sameSite, and proper production config
